## (A1 verbatim) — Architecture & module boundaries

### One-line pitch

Codex is OpenAI's lightweight, terminal-resident coding agent: a Rust core + a thin TS shim, distinguished from cline/aider/claude-code by (1) running fully locally with state in `~/.codex/`, (2) talking to OpenAI's **Responses API** (not Chat Completions) for richer streaming tool-call events, (3) shipping a real OS-level sandbox per-platform (Seatbelt / Landlock / Windows-sandbox), and (4) carrying its own DSLs — V4A patches and execpolicy rules.

### Black-box use case

```
$ npm i -g @openai/codex            # or: brew install --cask codex
$ codex                             # interactive TUI mode
> fix the failing test in pkg/foo
[codex reads files, decides to run go test, asks for approval, runs it,
 parses failure, edits a file via apply-patch, asks for approval to write,
 applies patch, re-runs test, reports back]
$ codex exec "summarise README"     # one-shot headless
$ codex resume                      # pick from rollout files in ~/.codex/sessions
```

### Sandboxing model (cited)

- macOS — `sandbox-exec` with a Seatbelt profile generated at runtime; entry in `codex-rs/sandboxing/` and `codex-rs/cli/src/sandbox.rs`
- Linux — Landlock LSM via `landlock_create_ruleset(2)` + `landlock_add_rule(2)` + `landlock_restrict_self(2)`, plus optional bubblewrap; entry in `codex-rs/linux-sandbox/`, `codex-rs/bwrap/`
- Windows — restricted token (`CreateRestrictedToken`); entry in `codex-rs/windows-sandbox-rs/`

### Persistence model

- `~/.codex/sessions/<uuid>.jsonl` — append-only rollout for the active session
- `~/.codex/archived_sessions/` — archived
- `~/.codex/history.jsonl` — global cross-session text history
- `~/.codex/config.toml` — config
- `~/.codex/log/codex-tui.log` — log
- (Newer code paths) `~/.codex/state_5.sqlite`, `logs_2.sqlite` — sqlite indexes that supplement the JSONL files

### Approval / patch model

- The model emits a tool call (e.g. `shell` or `apply_patch`).
- `core/src/codex_thread.rs` consults `approval_policy` (`Never` / `OnFailure` / `OnRequest` / `UnlessTrusted` / `Granular`) and possibly the execpolicy DSL.
- If approval needed: emits `EventMsg::ExecApprovalRequest` (or `PatchApprovalRequest`) and **blocks the turn** waiting for `Op::ExecApproval { approved }` from the frontend.
- Approved → tool runs (in sandbox for `shell`, or via `apply-patch` crate for patches).
- Counter: 3 consecutive denials or 10 total in a turn triggers an interrupt.

## (A2 verbatim) — Core mechanisms (12, will be merged into 10 chapters)

### Mechanism index

1. **Event Protocol** — `codex-rs/protocol/src/protocol.rs`. EventMsg enum (~30 variants: `TurnStarted`, `AgentMessage`, `ExecCommandBegin`, `ExecApprovalRequest`, `PatchApplyBegin`, `PatchApplyEnd`, `Error`, …) and Op enum (~20 variants: `UserInput`, `ExecApproval`, `PatchApproval`, `Interrupt`, `Shutdown`, `ReloadUserConfig`, …) plus `Submission { id, op, trace_context }`.
2. **Agent loop** — `codex-rs/core/src/codex_thread.rs`. `CodexThread::submit(op) -> SubmissionId` and `CodexThread::next_event() -> EventMsg`. Pull-based, not push-based.
3. **Rollout persistence** — `codex-rs/rollout/src/recorder.rs`. `RolloutRecorder` appends JSONL `RolloutItem`s. Writer is async and non-blocking.
4. **Model client (Responses API)** — `codex-rs/core/src/client.rs`. `ModelClient` + `ModelClientSession`. WebSocket streaming with HTTP fallback. Sticky routing via `x-codex-turn-state` header.
5. **Exec tool (shell)** — `codex-rs/core/src/exec.rs`. `ExecParams` + `process_exec_tool_call`. Streaming stdout/stderr, output cap (default 256 KB), timeout, sandbox-denial keyword sniffing.
6. **Execpolicy DSL** — `codex-rs/core/src/exec_policy.rs` and the dedicated `codex-rs/execpolicy/` crate. Starlark-style rules → `Allow / Prompt / Forbidden`.
7. **Guardian / approval** — `codex-rs/core/src/guardian/`. Risky actions get reviewed by a *nested CodexThread* (a separate model call) which returns a JSON decision `{ risk_level, outcome, rationale }`.
8. **Apply-patch (V4A)** — `codex-rs/apply-patch/src/lib.rs`. Hunks: `AddFile`, `DeleteFile`, `UpdateFile { path, move_path?, chunks }`. Each chunk has `old_lines`, `new_lines`, optional `change_context`. The DSL uses `*** Update File: <path>`, `@@`, `+ / - / (space)` markers.
9. **MCP bridge** — `codex-rs/core/src/mcp.rs` + `codex-rs/mcp-client/`. `McpManager` registers external MCP servers, tracks tool provenance, validates exposure rules before calling.
10. **Sandboxing adapters** — `codex-rs/core/src/sandboxing/` + `codex-rs/linux-sandbox/`. `ExecRequest { command, sandbox_type, sandbox_permissions }` dispatches to platform impl.
11. **TUI** — `codex-rs/tui/`. Ratatui multi-pane composer + chat + exec cells. (Not modeled in Go.)
12. **Session resume** — `codex-rs/tui/src/session_resume.rs`. Picker UI; CWD rebase; replay rollout items into a fresh `CodexThread`.

### Mental-model topics for Appendix A

1. **Local-first agent architecture** — terminal residency, `~/.codex/`, vs cloud-hosted (claude.ai) and IDE-resident (Cursor). Trade-offs: latency, privacy, offline.
2. **Responses API vs Chat Completions** — why Codex chose proprietary streaming. learn-codex picks the open path; explain the gap.
3. **Approval × sandbox** — two orthogonal axes (`approval_policy` for *when* to ask, `sandbox_mode` for *what's allowed* if it runs). Compare to Aider's auto-yes default.
4. **DSL-as-protocol-stability** — V4A patch and execpolicy chosen specifically to be parseable from LLM output without fuzzy matching.
5. **Comparison to peers** — claude-code (Anthropic, IDE-resident), cline (VS Code extension), aider (Git-aware CLI), Cursor agent. learn-codex is closest to claude-code in shape.
